# Critic 截图盲评

## 适用范围与调用

启用本 Skill 后，每轮视觉实现迭代及交付前使用 Critic。L1、L2、L3 的视觉交付都适用。四图参考仍直接展示并等待选择，纯非视觉任务和规范维护执行各自检查。

用户级配置位于 `~/.codex/agents/Critic.toml`。模型固定为 `gpt-6.1-terra`，推理强度固定为 `high`。配置中的 developer_instructions 是评审提示的唯一来源，各轮原样复用。主 agent 读取本指南掌握完成条件，向 Critic 提供的评审提示保持中立。

在当前实现的固定 browser-run 采集完成后运行。

```powershell
python '<skill>/scripts/verify.py' critic-run --root '<项目>'
```

Codex 不在 PATH 时通过 `--cli` 提供实际可执行文件。runner 加载 Critic 配置，建立全新、临时且无历史的会话，用同一固定请求提交当前截图。它关闭项目指令自动载入、记忆、Skill、应用、插件、MCP、搜索和代码执行能力。输入目录仅包含按顺序编号的当前截图，原始评审回复和过程记录保存在目录外。

同一任务的评审串行执行，重复并发调用返回受阻，进程结束后自动释放锁。任务已经替换时，旧评审保留自身记录，新任务的结果由对应任务继续维护。

## 输入隔离

截图来自当前任务真实 browser-run 凭证，覆盖已声明的页面、屏宽及状态。字节相同的截图合并提交，范围和原图对应关系继续保留。L3 使用完整页面，避免用局部裁切掩盖整体构图问题。L1/L2 已声明组件 root_selector 时，由真实浏览器额外采集该组件交给 Critic，完整页面截图继续保留用于相应验收，评审范围对应本次设计交付。

Critic 只收到当前截图与固定评审提示。源码、design.md、项目需求、参考方案、历史截图、历史评论、主 agent 的解释和期待分数都留在评审上下文之外。评分门槛、修复清单与批准状态也留在主工作流中。

## 主 agent 的迭代方式

一轮对应一批实际视觉修改。把当前反馈中可执行的问题统一落实后，再截图评分。critic-run 先完整核对最新一轮的截图、实现、任务、提示和执行凭证，相同版本直接返回原分数与 reused=true，高分和低分均如此。最终交付复用这一轮已核验评分，变化后的候选开启全新上下文评审。

1. 查看 Critic 对当前美学语言的判断、分数和最大差距，核对其指出的具体画面区域。
2. 优先处理整体结构、构图、比例、视觉重心和节奏，再修正字体、材质、图像与边缘等细节。对夸张、模板化或生成式套路采用具体改法，保持已选风格的审美立场。
3. 将反馈落实到原规则、已选风格及本次需求内。实际修改实现，更新相关决定，并重跑受影响检查。
4. 重新采集当前截图，在新的上下文用相同提示再次调用 Critic。下一轮只传新截图，修正说明和此前评论由主 agent 保管。
5. 当前独立评分达到 9 分及以上，并完成其他适用验收与批准后，才允许宣称任务完成。低于门槛持续改进，真实受阻时保留问题和 FAIL/BLOCKED。

保留原始分数，不将 8.99 四舍五入为 9，不手改评分、不挑选旧轮次高分，不通过重抽相同画面争取分数。无需为每次迭代另设用户审批。

## 记录与完成检查

每轮保留具体反馈、原始 JSON、执行流、实际使用的固定提示、截图绑定、模型、强度、任务和版本。任务下的 `critic/latest.json` 代表当前轮次，各轮 `critic/<round_id>/report.json` 保留历史。全局执行索引核对最新轮次，同一任务锁定首次使用的提示哈希。新评审先写待完成状态，异常与中断保留受阻，旧的通过结果随之失效。

交付验证器只校验当前评分与凭证，Hook 和 check 不自动发起模型调用。评分缺失、来源不匹配、截图或源码变化时保留 BLOCKED，当前有效评分低于门槛时为 FAIL。有效评分继续与原有逐项验收、独立合规复查及受保护批准一起判断。

最终复核与受保护批准材料包含当前 Critic 报告和执行记录。Critic 的截图美学判断覆盖可见结果，代码、行为、来源及真实设备要求继续由相应检查核对。本地凭证与验证器属于同一操作系统用户，受保护审批仍按 visual-approval.md 配置。
