# Image and asset workflow

## Style exploration
- Use the built-in Image tool (currently image_gen.imagegen), with the latest capability exposed by that tool. Do not hardcode an unexposed model version or substitute a third-party image endpoint. If the tool hides version selection, use its built-in default and state that the platform manages the version.
- For a new visual direction, generate four distinct A/B/C/D tone/style references and display them directly in the conversation with short theme labels. Include non-background visual ideas. They are style references, not final UI; no gallery, slideshow, thumbnail application or selection website is required.
- Keep this step lightweight: check visibility, obvious prohibited colors, useful direction differences and fit with the brief. Do not build an app, install a UI library, run browser QA, create a clause-by-clause acceptance dossier or request an independent review for references. Do not repeatedly edit incidental text or layout details in a mood reference. Regenerate only for a broken image, clearly wrong subject, prohibited colors, indistinguishable directions, or the user's requested change. Reuse already usable references.
- Wait for the user's selection before final design. A prior choice remains valid; local continuations may reuse a real prior choice. Existing branding alone is not evidence that the user selected a reference.

## Production assets
- Plan a coherent asset family against the actual page regions and content roles. Consider main scenes, subject objects, content illustrations, editorial images and applicable empty/success states. Choose relevant roles from the coverage gaps and record the purpose of each planned use.
- For L3 production, at least one built-in-Image-generated non-background content asset must be generated and used. This minimum establishes the required asset source. Judge the finished imagery by content coverage, composition and fidelity to the selected direction. Determine the asset count from those needs. Local L1/L2 changes apply the relevant scope.
- Query StyleKit resources first for suitable reusable patterns and source material. Record their availability, source, license and adaptation. Generate project-specific imagery through the built-in Image workflow and register actual use separately.
- Specify the scene or subject, composition, spatial layers, detail density, line/model complexity, material, lighting, palette, crop, negative space and final display size. Give the model concrete details drawn from the product: an interview preparation desk could include annotated notes, a timer and a partially used notebook, with distinct foreground, subject and supporting details. Choose the treatment from the selected reference; do not force a detailed realistic scene into a deliberately sparse or flat style. Use transparent output for independently placed objects, characters or stickers.
- Maintain shared palette, lighting, material and line treatment across the asset family. Give the main scene, supporting content objects and applicable state illustrations different jobs. One generic object duplicated into several regions, a background plus one token sticker, or several unused generated files does not establish coverage. Use scale, crop, layering and spacing to integrate the family; keep functional text and controls accessible and preserve the original logo.
- Build one major region with real copy, components, materials and planned imagery. Inspect it at its actual display size and narrow-screen size, compare the reference's color, material strength, image detail and density, then repair the affected choices before expanding the page. When a region feels empty, identify its missing content, image role or compositional layer and address that gap.
- Record generated files, real generation evidence, use sites and rendered loading/crop checks. Inspect images at their actual page size: details must remain legible, transparent margins must not shrink the subject, and cropping must retain the useful subject and texture. A hidden or effectively transparent image, an off-screen artifact or a network response alone cannot establish visible use. Optimize image dimensions/bytes for actual display size and check low-bandwidth behavior when material to the task.
- Shader and Tripo 3D use is optional and justified by the design. Do not describe a flat generated image as an interactive 3D model.

For L3 whole-page work, design_plan.asset_coverage records id, role, page, selector, purpose, decision=generate or omit, and reason. Cover the regions and states that need a visual decision. Link each generate entry to task.assets using the same id and role, with the actual file and render_check. Explain omit decisions in relation to the content and layout. The source record, actual loaded file and page screenshot remain the execution evidence. See design-document.md for the shared plan fields.

## Asset evidence and identity
For each production content asset task.assets records path, origin=builtin_image, role, purpose, generation_evidence, usage (implementation paths), and rendered url. Existing/user-supplied files use existing/user_provided origins and do not satisfy the generated-content requirement. A declared unsupported generator fails; recording builtin_image does not authenticate it. Consult actual Image tool history and output. No model version is invented when the tool does not expose one.

Use separate final assets after selection; an identical reference-image file cannot count as a production content asset. Fixed browser execution hashes the real loaded image response. The local asset hash must match that response and the image must appear in the rendered DOM. Optimized/reencoded output should be the registered production path, with its actual generation/derivation record. Missing inspectable media bytes (for example an untracked blob/canvas boundary) remain blocked for this identity check; do not substitute another image URL. The hash proves identity, not whether the image is attractive, transparent, well-cropped or useful. Review those in actual screenshots and relevant narrow-screen states.

## Shader and modeling decisions
For L3 production fill task.space_effects.shader and .model. Each has decision=used or omitted, and a concrete reason. They remain optional: do not generate a model or add a shader merely to satisfy a counter. When relevant local work uses them, fill the same records.

Used effects record usage implementation paths and render_check={page,width,state,selector}, corresponding to a real fixed-runner expect_visible assertion on the displayed scene/canvas. Generated models additionally record origin=generated, generator=tripo, path, generation_evidence and loaded url. Existing/user-provided models may use origin=existing/user_provided and must not fabricate generation evidence. Follow the available Tripo skill/workflow for actual generation and retain task/output evidence; do not invent task IDs, completed jobs or undisclosed versions. Keep real mesh files and source-generation records. A raster image cannot count as a model. Fixed browser execution checks actual loaded model bytes against the registered file, and checks that the declared render assertion actually ran. A visible canvas plus a loaded mesh does not prove that mesh rendered correctly; inspect the scene and interactions explicitly.

For shader/model adoption also inspect material/lighting fit, file/texture weight, mobile behavior, load/failure fallback and reduced-motion behavior when applicable. If generated output is unavailable or cannot be loaded/rendered, report the step unverified/blocked instead of claiming adoption. Omission needs a reason, not a fabricated generation call. A 3D workflow does not replace required built-in Image references/content assets.
