# 前端设计规则：拒绝流水线

版本：`7.0.0`。本次变更按版本号记录，详见 frontend-workflow 更新日志。

## 单一来源与执行入口
- 本文件是通用规则的唯一维护来源。全局 `AGENTS.md`、项目入口及其他工具入口只负责引导读取，不复制通用条款；项目文件补充具体需求。
- 每次修改通用规则时更新版本；项目记录注明实际读取的版本，不能凭记忆沿用旧版。
- 首条设计进度说明报告本文件的实际路径、已读取版本，以及“四张色调与风格参考 → 对话直接展示 → 用户选定风格 → 详细设计与实现 → 逐项验证”的流程。
- 无法读取时明确说明并尝试恢复；不得跳过读取。修改规则文件本身不触发四套生图流程。

## 读取时机
- 开始新的前端设计、网页或移动端 UI 设计、页面搭建、组件设计或视觉改版任务前，完整读取本文件、项目适用指引、需求资料和用户最新补充。同一任务与上下文内先核对文件哈希及最新补充，未变化的已读内容直接复用；规则变化、上下文缺失或新任务时完整读取。
- 本文件约束设计与实现；不得只在交付说明中复述。
- 本规则同样适用于风格选定之后的详细设计、编码、修改与交付；不得只执行首轮参考图流程。

## 适用边界与冲突处理
- 按本文件的强制项执行，不得用选定风格、组件库默认外观或实现方便来豁免；用户后续明确调整某项要求时，记录调整内容与适用范围。
- 非对称要求针对页面整体构图和多栏组织；左对齐、换配色或仅移动一个图标不足以证明落实。单栏移动端与表单可保持清晰顺序，页面仍须说明其构图节奏。
- “禁止等宽多栏”不默认豁免导航、工具栏或功能入口；确需等宽组织且与规则冲突时，明确说明并由用户决定例外，不自行放宽。
- 文字检查覆盖标题、正文、提示、按钮、协议与动态状态。逐项判断它是否帮助理解、判断或操作，删除重复说明、装饰性口号和无操作价值的文字。
- 保留品牌、用户要求原样保留的文案和必要协议。表达完整、准确、可理解，并清理无必要的附加说明。存在其他硬规则冲突时说明具体问题，由用户决定。
- 着色器与 Tripo 3D 为按需项；其他条款不得因“按需”字样被整体降为可选。项目资料中的单一风格参考不代表用户已经选定最终风格。

## 生图工具：统一使用内置 Image
- 所有图像生成与编辑统一使用内置 Image 生图工具（当前工具接口为 `image_gen.imagegen`），包括首轮风格参考与后续正式素材。
- 使用内置工具当前提供的最新可用模型能力，不写死模型版本，不切换第三方生图服务、自建接口、外部 API 或本地模型。
- 若内置工具支持显式选择模型，采用其中最新可用的图像模型；若未暴露型号或选择参数，直接使用内置默认能力，不虚构模型名称、版本或未提供的参数，也不因版本不可见而停工或转向外部服务。
- 若工具未披露实际型号，说明“使用内置 Image 生图，具体版本由平台管理”；不得声称已核实某个具体版本为最新。
- 若内置 Image 工具不可用，明确说明生图步骤受阻，保留该步骤；不得擅自换用第三方工具或以占位图冒充已生成图片。
- 本约定针对图像生成与编辑；按需使用的 Tripo 3D 仍只负责三维模型，不替代内置 Image 生图流程。

## 第一阶段：四套色调与风格参考
- 每次前端设计都先走风格选型流程，再展开详细的最终 UI 设计与实现。
- 先确定场景、用户、主要任务、内容密度与设备，再按场景查阅 StyleKit 的风格、字体、组件、布局和动效建议，记录适用依据及与原规则冲突时的适配。 生成四张参考前通过实际 CLI、MCP 或 HTTP 查询目录与候选详情，记录查询时间、来源、实际总数与分页，在轻量 style-discovery.json 中保存 A/B/C/D 的具体差异。
- 按“生图工具”约定，使用内置 Image 当前提供的最新可用模型能力，实际生成四套独立的色调与风格参考图，编号 A、B、C、D。
- 四套方案围绕同一需求探索不同视觉家族，每对方案至少在排版结构、字体体系、组件造型、材质/空间和图像语言中的三项形成具体差异，附动态交互意向；用简短对照确定这些差异再分别生图。
- 首轮图像用于选择色调、氛围与视觉风格，可采用情绪板、材质拼贴、字体意向与局部 UI 片段；不要求完整页面或最终布局。
- 每套风格参考同时探索非背景素材的视觉语言，例如角色、物件、场景插画或拼贴元素，展示该方向如何进入页面内容，避免四套都只展示不同背景。
- 每张图明确标注“风格参考，非最终界面”；生成提示词也必须说明探索用途，避免把参考图当成最终成品。
- 四张参考图使用一致画幅，快速确认可见、方向有差异、符合项目气质且无明显禁色；不把参考中的示例文字或局部排版当作正式 UI 验收，文案必要性、交互与响应式在正式页面验证。
- 直接在对话中展示四张图片，附 A、B、C、D 与简短主题；不生成浏览页、幻灯片、缩略图应用或选型站点。
- 参考阶段不安装组件库、不构建测试页面、不跑浏览器或独立验收，不逐字审核或反复修图；只有图像损坏、明显偏题、禁色、方向难以区分或用户要求时才针对性调整。
- 每套方案展示时附编号、实际采用的 StyleKit 风格名称与 slug、简短主题、配色色值和说明。图外图注完整标注风格，图内可用简短标记，确保用户能对应来源。
- 展示后明确请用户选择 A、B、C、D，或提出修改意见；用户未选定前，停留在风格探索阶段，不擅自选定、混合方案或开始最终设计与实现。
- 若用户要求调整，先修改对应参考图，再等待选定；用户明确要求融合方案时，先提供融合参考供其选定。
- 用户选定后，制作以项目 design.md 为执行依据，尽可能还原选定图片的配色比例、字体气质、构图节奏、组件造型、材质、光照与图像语言。按实际内容、可访问性与响应式要求落地，必要调整写入设计文档，关键文字和控件保留为可操作实现。
- 生图工具或模型版本存在限制时，按“生图工具”约定处理；不得虚构生成结果或型号核实情况。

## 第二阶段：选定风格后，落实全部规则
- 用户选定后，按“读取时机”核对当前规则、项目需求与用户最新补充，复用未变化的已读内容，再开始详细设计与制作。
- 在落实记录中保存“风格摘要”：选定方案编号、参考图路径或可访问引用、色值与配色比例意向、字体气质、材质、图像语言和氛围；注明未被批准的参考图布局及仍需独立设计的部分。
- 根据选定方向与真实内容独立设计信息层级、结构和交互，将对应 tokens、组件配方、模板或提示词适配到当前项目，在 design.md 记录实际来源、采用内容及冲突调整。 选定后锁定同一个 StyleKit slug，续作沿用。取得本页语言的完整 design.md，保留完整 Implementation Contract，原样纳入项目设计文档并追加本次适配和验收要求。已连接 MCP 时调用 stylekit_get_style 取得 brief，默认英文内容按目标语言改读对应文档链接。
- 正式视觉制作前先生成或更新项目根目录 design.md，记录场景、风格依据、design tokens、布局与内容、组件状态、动态交互、素材与验收计划，逐条保存设计决定和条件。启用 frontend-workflow 时将计划写入 checklist_plan JSON，检查后同步 implementation_checklist Markdown 结果。其他任务按范围维护逐项记录，保留用户已有内容。
- 清单记录规则版本，将适用条款逐条编号，并注明来源章节或原文；完整覆盖后才能开始编码，不得只挑容易完成的条款。
- 每项记录具体设计决定、实现位置、验证方法、预期通过条件与当前状态；状态区分“待做、已实现未验证、已验证、不适用、受阻”。不适用项必须说明原因。
- 编码前在进度说明中简述实际设计决定：不对称构图体现在哪里、字体层级如何安排、背景与材质如何实现、组件如何定制、生成素材如何参与内容表达。只写“高级、有温度、已遵守”不算设计决定；说明后直接制作，无需另设审批。
- 把规则落实为可执行决定：自定义色值与背景材质、非对称布局、字体与字重、必要且清楚的文案、组件库选型与深度定制、图标、非线性动效、生成素材、响应式与键盘操作。
- 检查表必须覆盖本文件所有要求及项目补充，不能只记录上述示例；强制项不得因省事标为不适用。着色器、Tripo 3D 等按需项须记录采用与否及理由。
- 使用 StyleKit 资源时核对实际官方查询、源码和依赖，记录版本或哈希、使用位置与适配。其他组件库与运行依赖通过 Context7 核实；受阻时查询官方文档并记录实际限制。
- 根据最终内容生成和使用实际素材；首轮风格图不能代替最终项目素材。需要保留的 Logo 和品牌资产按项目要求使用。
- 每完成一个主要区域，先实际操作动态组件，再对照 design.md、落实记录与风格摘要检查字体、构图、组件、素材和状态；修正可解决的偏离后再扩展。
- 风格选定后可直接推进详细设计、实现与必要验证，无需为每个常规步骤另设用户审批；实质冲突或缺失信息影响结果时，明确指出具体问题。

## 设计立场
- 以资深独立设计师的判断做事，追求有温度的网页。
- 拒绝千篇一律的 SaaS 模板，每个像素都应服务于表达。
- 每次随机探索不同的配色、布局、字体与材质组合。
- 用随机探索形成四套符合项目定位的候选风格；用户选定后稳定执行该方向，每套方案内部保持视觉一致。

## 配色与背景
- 禁止紫色、靛蓝色、蓝紫渐变，包括 `#6366F1`、`#8B5CF6`。
- 禁止直接使用 Tailwind 默认色板；自定义项目色值与设计变量。
- 禁止纯平背景；必须使用噪点纹理或渐变，可组合纸张、颗粒等材质。按选定参考逐区域还原颜色职责、面积意向、明暗饱和度与冷暖关系，以及纹理尺度强度、光照、边缘和阴影；不得把不同风格统一成浅淡纸纹。恒色渐变或完全透明的纹理不算可见材质。
- 示例方向：骨白配锈红、墨绿配奶油黄、炭黑配铜橙；示例不是固定模板。

## 布局与字体
- 禁止“Hero + 三卡片”的模板布局。
- 禁止全页完美居中；用偏移、错位、留白建立节奏。
- 禁止等宽多栏；使用不对称的宽度、大小或位置关系。
- 每次探索适合场景的字体风格，按选定方向尝试艺术字体用于品牌或标题，中文与拉丁字体、真实字重及回退协调。核对字体许可、加载与实际文字表现。正文和必要说明保持可读，通过删重复文案、合并提示及调整间距维持紧凑，记录字号、行高和目标尺寸下的实际阅读结果。 正文与必要说明禁止使用微软雅黑、Microsoft YaHei、Microsoft YaHei UI 及其别名或实际回退。按场景比较思源黑体、Arial、Tahoma、Georgia、霞鹜文楷及其真实 Medium 资源、Noto Serif SC、Mantou Sans 等候选，分别确定正文、标题与品牌角色，核对中文覆盖与实际渲染。
- 不对称布局仍需保证阅读顺序，并适配窄屏。提取选定参考中本次适用的内容与操作组合、区域比例、进度嵌入位置、曲面和边缘关系，映射到实际组件及窄屏安排。对照关键组合与局部光影，修正脱离参考的常见图文卡片化处理。

## 页面文案
- 口语化，像朋友聊天；允许幽默、自嘲和适度挑衅。
- 文案以必要、清楚、准确为准。检查每段文字对当前任务的作用，删除用户读完也无法据此理解、判断或操作的空泛句。必要说明可按语义完整表达。
- 使用具体场景和有依据的数字；不得编造销量、评价或效果数据。
- 禁止高深术语、空话、Lorem Ipsum、无意义解释、重复提示和空泛鼓励。优先主动表达，让必要内容容易理解。
- 示例：“午休就剩十分钟。”“三步，收好账单。”

## 组件与动效
- 禁止直接套用 Shadcn 或 Material UI 默认外观；使用时必须深度定制。按钮优先采用并适配 StyleKit 动态资源，按选定材质设计 hover、focus、pressed 及实际存在的 loading、success、error、disabled 反馈，使用非线性动效。视觉变化与真实操作结果分别验证；无效果点击、仅找到原按钮或统一透明度变化不能代替所需的交互与视觉表现。
- 禁止用 Emoji 作为功能图标；采用风格统一的 SVG 或图标库。
- 禁止线性动画及 `ease-in-out`；按场景选择弹簧、非线性缓动或自定义曲线。 新页面和完整改版的每个页面都须规划服务主要任务的动态组件，写明触发、前后状态、缓动与减少动态效果处理，并实际操作验收；纯背景运动或统一 hover 不能替代。 编码前优先评估现有引擎、可复用动态组件及 Motion/GSAP，记录选择与文档依据，并规划鼠标交互、触屏/键盘回退、reduced-motion 和卸载清理。
- 新页面、完整 UI 改版及适用新组件优先查询并使用 StyleKit 自带资源库的组件配方、动态组件和模板源码，核对源码可用性、许可、依赖与场景。实际 StyleKit 资源可作为主要组件来源，记录获取依据、适配代码与渲染结果。缺少合适资源时说明具体原因后使用补充库。
- StyleKit 资源优先。需要补充时从 Magic UI、Aceternity UI、DaisyUI、Brutalist UI、Glass UI、Radix UI、Mantine 中选择适合项目的组件库。局部文字和简单样式修改按影响范围处理，保留真实已有选型。
- StyleKit 通过实际 MCP、CLI 或官方文档取得资源，记录来源、版本或哈希与使用位置。其他引入的组件库及运行依赖通过 Context7 核对版本、安装方式与 API，受阻时核对官方文档并记录实际限制。

## 图像与空间效果
- 统一使用内置 Image 当前提供的最新可用模型能力，生成贴合项目的个性图像；具体执行遵守“生图工具”约定。
- 实际生成并使用素材，不得用空白框或占位图冒充成果。
- 风格选定后先按内容角色建立成套素材计划，写明每张素材的主体或场景、用途、页面位置、构图层次、细节密度、线条或建模复杂度、材质光照、实际展示尺寸、透明需求与风格依据，再实际生成并融入页面；仅生成背景图不能算完成图像要求。不能把每次一张简单物件当作完成，按主场景、辅助物件或状态表达的真实缺口补充，不设固定数量配额，不靠堆图填空。
- 根据项目内容组合多类素材：主视觉、场景插画、角色或吉祥物、独立物件与透明贴图、编辑式拼贴、章节装饰、空状态或成功状态插画，以及纸张等纹理。按需要选择，不要求全部堆进同一页面。
- 正式页面至少实际使用一项由内置 Image 生成的非背景内容素材，直接服务产品场景或内容表达；背景、噪点纹理、原有 Logo、未使用文件及首轮参考图均不能单独充数。
- 素材提示词具体描述角色或物件、构图与裁切、风格、光照、色调、留白和输出用途；需要独立摆放的角色、物件、贴纸等使用透明背景，编辑时按需求保留透明度。
- 一套素材保持配色、光照、线条或材质一致，并通过尺度、裁切、叠放、局部露出及留白参与构图；素材数量服从信息层级，不能遮挡文字或妨碍操作。先在真实展示尺寸检查主体、次级细节、层次与场景辨识度，再按覆盖缺口补齐；同图重复或透明未显示的素材不能冒充内容覆盖。
- 功能文字和关键操作保留为真实 HTML 与可访问控件；功能图标优先使用清晰、统一的 SVG，不将整张生图当页面、按钮或表单，不以装饰素材替代功能含义。保留用户提供的 Logo。
- 素材记录包含用途、真实文件、生成依据、代码使用位置、实际加载 URL 和对应页面截图；核对图像能加载、裁切合适、窄屏表现与体积成本。是否有个性和适合内容须实际查看，不能由文件存在推断。
- 考虑着色器或 Tripo 3D，以增强材质、空间感与趣味；按项目需要选用。
- 动效与 3D 应服务内容，兼顾加载成本、移动端与减少动态效果偏好。

## Critic 美学评审
- 启用 frontend-workflow 后，每轮视觉实现迭代与交付前，以当前真实截图调用 Critic，模型使用 gpt-6.1-terra，推理强度 high。每轮使用全新上下文与同一固定评审提示，只提供当前截图，隔离代码、需求文档、早期版本、历史评论和主 agent 的期待分数。参考选型、纯非视觉任务及规范维护按各自范围执行。
- Critic 独立评估当前美学距离顶尖设计工作室完成度的最大差距，兼顾整体结构、构图和细节，对夸张、模板化及明显生成式视觉套路给出有依据的扣分。反馈明确指出具体区域、问题、影响与改法，保持胆识和审美立场，以满分 10 分给出当前评分。
- 主 agent 仅在当前独立评分达到 9 分及以上并通过其他适用验收与批准后宣称完成。评分不足时实际修正、复测并重新截图，以同一提示在新上下文重评。9 分完成门槛保留在主工作流与验证器，评审提示不披露该门槛；原始评分、实际调用、截图和当前版本绑定，变更后复核，禁止改分、四舍五入凑分或挑选旧高分。

## 交付前核对
- 首轮快速核对四张真实风格参考、主题差异、参考用途与编号，直接展示供选择；最终阶段核对真实选型，完整验收正式页面而非参考图。
- 核对禁色、背景、非对称布局、字体、文案必要性、组件定制与图像是否符合规则。
- 检查主要屏宽、文字可读性、键盘操作与动效表现。
- 对照实际渲染页面与源码逐项验证落实记录：核对色值、背景、布局、文案必要性、图标、动画缓动、组件定制与素材引用，并在目标屏宽检查交互及视觉表现。
- 为已验证项记录实现路径、实际查看的页面或截图、运行检查等相应依据；代码已写不等于视觉与交互已验证，无法运行的项目必须标记未验证。
- 强制项未完成或验证失败时，继续修正可解决的问题；存在阻碍时明确列出未完成项与原因，不得宣称已全部落实。
- 简述本次视觉方向，以及实际采用的素材、组件库和空间效果。
- 交付说明附落实记录的位置，简述验证结果与尚存缺口，让用户能核对规则执行情况。

## 验收说明：通过之后才算完成
- 制作前、关键页面完成后和最终交付前分别检查；关键页面未通过的可解决问题先修复再扩展，最终强制项未通过时继续修改并复查，不提前结束为“已完成”。 每次交付前再做一轮规则落实与改进复核，记录实际观察、已识别问题、修正和复测结果。当前需求范围内仍有可执行改进时继续修正并复核，直到没有已知缺口及已识别可执行改进项再交付。确有阻碍时保留具体缺口与原因。
- 分开执行源码检查与实际页面检查；文件包含了规则、检查表已填写、项目能编译或测试通过，都不能单独证明 UI 验收通过。
- 对可量化要求尽量运行轻量脚本或现有检查：扫描禁用色值与默认色板引用、提取实际展示文案并检查重复和空泛口号候选、检查 `linear` 与 `ease-in-out`、占位内容及素材引用。排除无关文件与注释干扰；动态文案、主题变量及第三方样式需结合实际渲染复核，扫描无命中不能证明全面合规。
- 对视觉要求实际查看目标屏宽下的页面或截图：检查非对称构图、字体层级、背景材质、组件定制、素材表现及与选定风格的一致性。指出体现这些要求的具体区域，不能只写“看起来符合”。
- 对功能要求实际操作关键流程、组件状态与键盘路径；按任务覆盖窄屏和其他目标尺寸，记录实际测试范围。仅提供静态设计时，交互实现标为未交付并注明任务边界，不冒充已验证。
- 每项落实清单同步实际结果、实现位置、通过条件与证据，未执行的项目保留未验证，失败项目修正后复测。浏览器用例逐项对应其检查对象，交付前清理遗留待做项与通用结论。适用的真实触屏、完整焦点路线和屏幕阅读器检查记录设备、工具、步骤、结果及缺口，缺少实测保留受阻。
- 修改后重新检查受影响条款与页面；无需反复运行与改动无关的全部检查，也不得以未更新的旧截图证明新实现通过。
- 交付时简述已通过、未通过和未验证的内容，提供落实记录及必要截图或检查结果的位置。未通过项写清具体问题、原因及后续处理，不用百分比或笼统承诺代替逐项结果。
- 风格摘要和验收记录是制作过程中的工作材料；除已规定的风格选择与真实冲突外，不增加用户逐步审批负担。

## 工作流检查机制（仅明确启用）
- 本文件是设计要求的唯一来源，前端任务仍先完整读取本文件。仅用户明确调用 frontend-workflow 后才加载 `SKILL.md`；未调用时不自动加载该 Skill。停用工作流不取消本文件的设计要求。
- 显式启用后的检查器为 `<skill>/scripts/verify.py`；项目清单与结果使用 `work/frontend-policy/task.json`、`work/frontend-policy/result.json`。未启用时不强制建立专用清单或运行专用门禁；旧 frontend-gate 路径停用。
- 启用检查器时，原文件进入策略哈希；修改后旧任务证据失效。原条款与检查路由逐条绑定，新条款未映射时阻断该工作流验收，不因文档更新自动声称已经覆盖。
- 工作流启用后的分级只限制工作范围：L1/L2 检查本次修改适用条款，L3 检查声明页面。分级不关闭范围内的硬性要求；既有品牌冲突须明确指出并取得用户对具体例外的决定。
- 新的视觉设计先走四套风格参考和用户选定流程；对已选方案的延续及局部修补可沿用真实既有选型记录，不重复生成无关方案。L3 正式页面需记录选型依据、风格摘要及素材计划，并落实非背景内容素材。
- 全局 Hook 只跟随当前任务的明确启用及其续作；普通前端需求、UI 文件改动、仅提到或询问 Skill 不激活工作流。用户停用或开始无关新任务后不沿用启用状态。Hook 信任及真实激活仍需单独核实。
- 启用后由固定 browser-run 程序实际操作、断言和采集；导入 DOM 与截图仅用于诊断。脚本运行凭证不等于所有设计条款通过，更不能自动证明审美和生成来源。
- 启用后的 task.rule_application 逐条注明适用、范围外或条件项及理由；适用的主观设计条款提供观察。缺少独立验收不能以模型自评授予总体 PASS。
- 仅启用后的 Stop 执行专用交付检查，最多自动补救两次，之后保留真实失败或受阻结果。未启用的任务不因缺少该工作流记录而被拦截；任何情况下都不得制造证据或虚报完成。
